# Personal AI OS v0.6 产品研究

## 结论

通用 Agent 已经能够调用工具、保存记忆、定时运行、派生子 Agent，并在中断后恢复。Personal AI OS 没有必要重复建设这些能力。v0.6 更值得验证的是一层长期工作控制系统：它读取现有工作区，整理模块和依赖，把目标转换成可接续的任务；执行过程中保留约束、证据和人工决定，使不同模型、不同会话和不同机器能够继续同一项工作。

秘书能力也应围绕工作连续性展开。当前实现已经能从 SQLite 运行快照生成简短 Secretary brief，并把待决定、待验收和待分派事项排成最多三项下一动作。任务停滞、证据过期、执行者退出和承诺遗漏的持续检测仍是待验证能力。邮件摘要、日历排期和会议纪要可以作为接入模块，但不构成产品的主要差异。

本文依据公开产品文档、开源仓库和长任务评测整理。竞品能力以文档明确说明为准；没有公开证据的能力不作推断。Personal AI OS 的“当前实现”以本仓库源码和测试为准；研究假设、验收线和后续能力不代表已经实现。

## 当前实现基线

v0.6 当前工作树已经落地以下最小运行链路：

- SQLite 持久保存工作流、任务、运行、事件、模型输出产物和人工决定；
- 模块地图支持把选中模块的批注转成当前工作流中的修正任务；
- 下游模型会收到当前任务上下文和已完成依赖的当前验收产物，旧产物不会与当前结果混入同一个交接包；
- Execution Broker 校验依赖、Human Gate、Adapter 可用性和外部运行 ID；
- Python 标准库 HTTP server 向同一 Workbench 提供有限 JSON API；
- OpenAI-compatible Chat Completions Adapter 同步执行一个有边界的任务，并把终态结果送入 `REVIEW`；
- Secretary context pack 只携带必要字段和引用，brief 从 runtime-store 汇总状态与下一动作；
- 静态匿名演示与真实本地运行投影具有不同的数据来源标识。

当前没有 SSE、后台流式执行、运行取消与续接、模型自动发现、Codex App Server / VS Code Adapter、远程执行控制或自动全仓分形扫描。Secretary brief 是按需快照，不是定时运行、主动通知或自动 Domain 路由。

## 长任务为什么仍然失败

[OSWorld 2.0](https://osworld-v2.xlang.ai/) 收录了 108 个真实长流程任务。人工完成这些任务的中位时间约为 1.6 小时，69.6% 的任务需要一小时以上；使用 Claude Opus 4.7 最大思考强度时，每项任务平均约有 318 次工具调用。该评测报告显示，在 500 步限制下，最佳参评系统的完整完成率仍为 20.6%。

失败通常发生在工作连续性上。Agent 会丢失早先约束，忽略中途出现的新信息，面对隐含状态时自行猜测，或在完成一连串操作后跳过最终核验。跨来源推理也很常见：46 个任务要求从邮件、文档、网站、历史记录等多个来源核对事实。

[METR 的时间跨度评测](https://metr.org/time-horizons/) 同样把成功率作为核心指标。其“50% 时间跨度”表示模型对相应难度任务只有一半成功概率，而不是模型能够稳定独立工作那么长时间。METR 也说明，其当前任务主要来自软件工程、机器学习和安全领域，超过 16 小时的估计并不可靠。这提醒产品团队：长时间运行、产生大量调用或显示繁忙状态，都不能替代结果验收。

运行轨迹也不能单独证明任务完成。[OpenAI 的 Trace Grading 指南](https://developers.openai.com/api/docs/guides/trace-grading) 把轨迹评分定义为对端到端决策、工具调用和推理步骤的结构化评价；[Anthropic 的 Agent Evals 指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 则把输出、工具调用和中间过程共同纳入评测。两者都指向同一个产品要求：系统既要记录发生了什么，也要检查结果是否正确。

## Personal AI OS 的产品差异

### 从工作区生成可操作的系统地图

首次接入后，系统应读取代码、文档、接口和已有任务，生成模块、输入输出与依赖关系草案。地图允许逐层进入模块内部，问题批注可以转成任务。用户负责修正系统理解，不需要从空白画布开始搭图。

这一能力与流程编辑器不同。流程编辑器描述计划怎样运行；系统地图说明当前工作区实际上由什么组成、哪些依赖已经存在、哪里仍是未知。

### 用任务包维持工作连续性

任务卡需要成为可移交的工作包，至少包含：

- 目标和完成标准；
- 当前阶段、依赖和阻断原因；
- 已使用的材料、已验证事实和仍待核验的内容；
- 不可越过的权限或数据边界；
- 执行记录、产物位置和下一次恢复动作。

新模型接手时应先读取任务包，再按需加载材料。完整聊天记录只能作为历史证据，不应成为恢复任务的唯一入口。

### 把人工介入整理成决策包

待决定事项不应只显示“批准”或“拒绝”。每个决策包需要说明触发原因、证据、可选路径、成本和影响范围。用户作出选择后，决定应更新任务状态，并生成明确的恢复动作。

高风险动作需要预先批准；信息不足时，任务进入 `UNKNOWN` 或等待补充，不允许系统用猜测填补状态。

### 保持执行器可替换

模型、Agent 框架、本地工具和远程机器都作为可插拔执行器。任务包和状态转换不依赖某一家模型。路由层根据任务类型、成本、工具需求和权限选择执行器，执行结果回写统一状态。

v0.6 无需同时适配所有平台。一个任务能在两种模型和两个运行环境之间可靠移交，已经足以检验接口设计。

### 把秘书职责放在持续工作上

当前 Secretary brief 已经读取同一运行快照，统计进行中、待验收、阻塞、暂停、待分配和待决定状态，并优先给出决定、验收和分派动作。它不读取记忆正文，也不执行外部动作。

后续秘书巡检需要验证四类异常：

- 已超过预期时间且没有新证据的任务；
- 因模型退出、机器不可用或权限不足而中断的任务；
- 中途出现新材料，导致原计划或结论可能失效的任务；
- 已产生输出但没有通过验收的任务。

默认输出应是简短的变化摘要和待决定事项。没有变化时保持安静。定时检查、变化比较、主动通知以及日历、邮件或消息接入目前尚未实现；新增接入只负责提供事件和执行用户授权的动作。

## v0.6 MVP 验证闭环

当前同步 runtime 已覆盖任务持久化、一次兼容模型调用、结果登记、人工验收与决定记录。完整产品假设仍需用一个真实、可重复的长任务验证：

1. 接入一个结构混乱但边界明确的本地项目。
2. 生成模块地图、依赖草案和材料分类建议。
3. 用户修正地图，并选择一个可以在数小时内验收的目标。
4. 系统生成任务树，为每个任务写入输入、输出、执行器和完成标准。
5. 两种模型分别执行独立任务，结果回写统一状态。
6. 人为制造一次会话终止和一次运行环境切换，验证恢复能力。
7. 在一个高风险动作前触发决策包，记录选择并继续执行。
8. 对最终产物执行验收；未满足标准的任务重新进入工作队列。
9. Secretary 先输出当前 brief；后续巡检实现再验证变化、阻断和待决定事项，且不重复报告无变化的正常任务。

这个闭环检验的是系统能否维持工作连续性。页面数量、动画数量和模型调用次数不作为成功指标。

## 可证伪的 MVP 假设

| 假设 | 测试方法 | v0.6 验收线 | 判定失败 |
| --- | --- | --- | --- |
| H1：新执行者可以快速恢复现场 | 在任务进行中更换会话和模型，禁止新执行者读取完整聊天记录 | 10 分钟内开始有效工作；重复已完成步骤为 0；关键约束保留率 100% | 需要维护者重新口述背景，或再次执行已经完成的动作 |
| H2：系统能从工作区生成有用的结构草案 | 在实现有资源上限的自动扫描后，由维护者先写一份顶层模块和关键依赖清单，再与自动结果盲比 | 顶层模块召回率不低于 80%；关键依赖召回率不低于 80%；高风险材料误分类率低于 10% | 地图主要依靠用户从头重画，或漏掉会改变执行路径的依赖 |
| H3：决策包能减少重新阅读材料的时间 | 记录每次人工裁决是否需要另开原始文件，以及裁决所用时间 | 80% 的裁决只看决策包即可完成；中位裁决时间不超过 2 分钟 | 用户经常需要重新检索聊天和文件才能理解问题 |
| H4：任务可以跨执行器移交 | 同一任务包分别交给两种模型，并在本地和远程环境各恢复一次 | 四次恢复都保留目标、约束、材料引用和完成标准；无未经授权的写入 | 状态格式依赖某个模型，或更换环境后无法判断已完成工作 |
| H5：Secretary 主动提醒有实际价值 | 在快照 brief 之上增加巡检后，先运行两周 shadow mode，只记录提醒，不自动发送或执行 | 提前发现至少 70% 的真实停滞或遗漏；提醒准确率不低于 80%；每 8 小时无关提醒不超过 3 条 | 提醒以重复状态播报为主，或漏掉多数真实阻断 |
| H6：验收闭环优于“执行即完成” | 对同一任务分别采用普通完成状态和证据验收状态，对比返工 | 所有完成项都有对应产物与检查结果；因漏验造成的返工下降 50% | 系统仍把工具退出成功、模型回复结束或文件存在视为完成 |

## v0.6 不做什么

- 不自建通用聊天模型或推理服务。
- 不以工具、插件和模型接入数量衡量版本价值。
- 不重做通用浏览器、终端、MCP、定时器和子 Agent 运行时。
- 不把静态看板、拖拽节点或宠物动画当作长任务能力证明。
- 不把邮箱摘要、会议纪要和日历排期包装成完整秘书产品。
- 不用 trace 数量、token 消耗或运行时长替代产物验收。
- 不在用户确认前执行删除、发布、付款或外部发送等高风险动作。

## 产品决策建议

v0.6 的优先级应按一个问题排序：它是否让一项真实长任务更容易继续和完成？

当前任务包、状态转换、SQLite 恢复、决定记录、同步兼容 Adapter 和 Secretary brief 已形成最小基线。下一优先级是后台运行生命周期、持久事件游标、SSE、取消与断线恢复；随后才是更多执行器、模型发现和自动工作区地图。Secretary 的主动巡检先以 shadow mode 验证，再考虑通知或自动操作。

可视化界面服务于这套状态模型。全局地图回答系统由什么组成，工作面板回答任务如何推进，待决定队列回答哪里需要人。三者读取同一份权威状态，避免分别维护互相矛盾的展示数据。

如果上述六项假设不能在真实项目上达到验收线，v0.6 应缩小范围，继续修正任务语义和恢复机制，而不是增加更多 Agent、工具或页面。
